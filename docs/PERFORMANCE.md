# PERFORMANCE — FuelPro
Measured 2026-11-24 for 0.26.0. Every number below comes from a script in `scripts/` that anyone can run again; labels as in CLAUDE.md §11 (all VERIFIED unless said).
Rule: **measure → change → prove identical answers → measure again** (`.claude/skills/fuelpro-performance`). No balance or report is cached (ADR-23).

## 1. Conditions
- Machine: Claude cloud container, 4 vCPU Intel Xeon 2.1 GHz, 16 GB RAM, Linux, Node 22.23.5, Chromium 1243 (Playwright). Server and benchmark client in one process (the client's JSON parsing is included in API times).
- Data: (a) **real-data snapshot copy** (`dev-data/fuelpro-snapshot.db`, one station, 13,857 journals, 61,725 journal lines, 11,881 sales; password-free); (b) **demo 4 years**: 98,912 journals, 366,148 lines, 83,806 sales, 2 stations; (c) **demo 20 years**: 481,222 journals, 1,781,760 lines, 407,937 sales, 514 MB. Demo data is generated by `scripts/seed-demo.js` through the real business logic (no real customers).
- "Before" = commit `08f51ff` (0.25.0) on the same database converted back to the v15 index set; "after" = 0.26.0. Both runs back to back.
- API: `scripts/bench-api.js` (37 read requests of the main screens, 30 runs each on (a), 10 on (b), 5 on (c); ms). Screens: `scripts/bench-pages.js` (each menu screen opened 3 times, median; ms from opening until the screen replaced its skeleton). Profiles: **desktop** (no throttling, 1366 px) and **phone** (4× CPU slowdown, 1.6 Mbps, 150 ms latency, 390 px).
- Same answers: `scripts/compare-dump.js` on every response — **all responses identical** before/after on (a) and (b).

## 2. Causes found (Phase 1 analysis)
| # | Cause | Where | Effect measured |
|---|---|---|---|
| 1 | No compression, no ETag on app files | `src/server.js` `serveStatic` | every reload re-downloaded 533 KB (phone: 3.7 s) |
| 2 | Alert check after **every** screen change, 165 ms of blocking work | `public/alerts-ui.js`, `src/alerts.js` | the next screen's request waited for it: ~200 ms floor on every screen |
| 3 | N+1 queries: 3 queries per customer in ageing, 1 per customer in integrity / customer list / dashboard | `src/ops.js`, `src/services.js` | ageing 73 ms, integrity 66 ms, customers 21 ms (148 customers) |
| 4 | Balances: every journal line joined to its account before grouping | `balances()` in `src/ops.js` | trial balance / income statement / balance sheet ~40 ms, analytics 4 calls |
| 5 | Ledger: 5 correlated sub-queries per line | `accountLedger` | 129 ms for 12k lines (+ 5 MB JSON uncompressed) |
| 6 | A new `Intl.NumberFormat` / `DateTimeFormat` for every amount and date shown | `public/*.js` (16 places) | 36k constructions for one ledger |
| 7 | Column auto-fit forced up to 3 full layouts **per table** | `fitTable` in `public/app.js` | 97% of its time; 100 journal cards = 300 layouts |
| 8 | Thousands of rows put in the DOM at once | journal book, journal list, statements, GL, sales register | phone: journal book 9.3 s, accounts 4.5 s |
| 9 | Reload asked for 17 files one by one (304s, but one round trip each) | `index.html` | phone reload 1.6 s after fix 1 |
Not found: memory leaks (JS heap 7–15 MB on every screen), unnecessary re-rendering loops, duplicate dependencies (runtime dependency: `pg` only, loaded lazily).

## 3. What changed (0.26.0)
Server: brotli/gzip + ETag/304; content-hashed `?v=` URLs with `immutable` caching; API gzip ≥ 1.4 KB; schema v16 covering indexes; grouped queries (`partyBalances`, `partyExtrasMany`, ageing); balances aggregated per account first; ledger joins; integrity per-journal probe; cash-flow plan hint. Front end: `FPFMT` cached formatters; table fitting in 3 rounds for the whole screen; long lists in parts with «show more / show all» (printing, PDF, Excel keep every row); bell re-check at most every 2 minutes. Fixes found on the way: boot race (KI-13), CSP-blocked styles (KI-14), (date, id) paging (KI-15), double submit (KI-16).

## 7. Concurrency (scripts/stress-api.js, 20 users, no pause between requests)
| Data | Throughput | 5xx | Sales / retries | Duplicates | Books after |
|---|---|---|---|---|---|
| demo 120 days | 250 req/s; p95 49 ms (sale), 112 ms (trial balance), 489 ms (month ledger) | 0 | 820 sales, 230 retries all answered with the first sale | 0 | balanced, integrity OK |
| demo 20 years | 14 req/s; p95 1–7 s (every request queues behind the heavy ones) | 0 | 60 sales, 23 retries all answered with the first sale | 0 | balanced, integrity OK |
One Node process answers one request at a time (by design: one request = one uninterrupted transaction). At 20 years a trial balance (~330 ms) or an opening balance over 20 years of lines (~110 ms) holds everyone else up; correctness is unaffected.

## 9. Next (measured, not done)
1. **Summary totals for 7+ years** (KI-17): a `daily_account_totals` table written by trigger in the same transaction as each posted journal line (never a time cache, ADR-23) would make trial balance, balance sheet, opening balances and the integrity sums O(days) instead of O(lines). Needs its own migration, a backfill and a reconciliation test against Σ journal_lines.
2. **Heavy reports off the main thread** (or a second read-only connection in a worker) so one report does not hold up a cashier at 20 years.
3. **Server-side idempotency key** (`Idempotency-Key` header stored with the answer) for vouchers, payments, expenses — the UI double-tap is fixed (KI-16), a lost network answer followed by a manual retry is not.
4. Journal book on a phone: 2.7 s for a 2,000-line month; a smaller first part (e.g. 80 entries) would bring it under 2 s.
