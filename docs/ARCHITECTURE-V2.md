# FuelPro v2 — الوثيقة المعمارية (المرحلة 0)

التاريخ: 2026-11-27 · الحالة: **مقترح ينتظر مراجعة المالك** · القرارات: ADR-30 إلى ADR-38 في `docs/DECISIONS.md`.
كل رقم هنا **مقاس** في هذه الجلسة (VERIFIED)، إلا ما وُسم «منقول» (REPORTED) من مصادر منشورة. الكود والنتائج الخام: `bench/arch-v2/`.

## 1. الخلاصة في سطور
1. **منتج واحد، ثلاثة أنماط مستقلة، ونواة واحدة.** المنطق المحاسبي كله في نواة TypeScript واحدة (`core`) تعمل كما هي في الأنماط الثلاثة. يختلف فقط «محوّل التخزين» والغلاف. لا مزامنة بين الأنماط؛ النقل بينها بملف نسخة احتياطية يدوي.
2. **السيرفر: Node.js + TypeScript + PostgreSQL 16.** ليس لأن Node الأسرع (Rust وGo أسرع وأخف ذاكرة)، بل لأنه **الوحيد الذي يسمح بأن تكون نواة المحاسبة نفسها في السيرفر وفي تطبيق الحاسوب والهاتف**، فتكون الأرقام مطابقة بالمليم بالبناء لا بالاختبار وحده. والقياس أثبت أنه يكفي: p95 أقل من 60 مللي ثانية للقراءات والكتابات الشائعة تحت 100 اتصال.
3. **المحلي: SQLite.** الحاسوب: **Tauri 2** (غلاف صغير يستخدم متصفح النظام). الهاتف: **Capacitor** مع SQLite أصلي. الواجهة نفسها في الثلاثة.
4. **الواجهة: نبقى بلا إطار (vanilla) مع TypeScript وخطوة بناء.** القياس: لا إطار أسرع من الكود الحالي على هاتف ضعيف؛ الأطر تكلف 4–6 أضعاف الذاكرة. الحل الحقيقي للجداول الكبيرة هو «العرض الافتراضي» (virtualization).
5. **أكبر مشكلة أداء حالية ليست اللغة بل التقارير الثقيلة** التي تحجب خيط Node الوحيد: تحت 100 مستخدم، p95 للعمليات الشائعة 250–290 مللي ثانية لأنها تنتظر خلف دفتر الأستاذ (3.1 ثانية). الحل: تشغيل التقارير في عمّال (worker threads) منفصلين + فهارس، وهو أول ما يُنفّذ.
6. **الترحيل تدريجي (strangler):** النظام الحالي يبقى حياً بلا مساس. الجديد يُبنى بجانبه وحدة وحدة، وأداة ترحيل تتحقق من الدفاتر وتتوقف عند أي فرق.

## 3. مقارنة الخلفية وقاعدة البيانات (مقاس)
نفس الخدمة في 6 تقنيات، نفس البيانات (1.2 مليون بيع، 4.8 مليون سطر قيد، منظمتان × 3 محطات)، 100 اتصال، 15 ثانية. التفاصيل: `bench/arch-v2/backend/REPORT.md`.

| التقنية | قائمة 50 بيع p95 (SQLite / PG) | بيع كامل في معاملة: req/s و p95 (SQLite / PG) | ذاكرة السيرفر | حجم ما يُنشر |
|---|---|---|---|---|
| Node node:http | 28.9 / 28.8 ms | 4666, 31 ms / 2608, 51 ms | 85–119 MB | Node 118 MB + 0.9 MB |
| Node Fastify 5 | 22.1 / 26.6 | 4648, 31 / 2839, 52 | 90–139 MB | + 15.9 MB |
| Node Hono | 27.9 / 26.1 | 3827, 37 / 2308, 58 | 60–160 MB | + 5 MB |
| Bun Hono | 12.1 / — | 5014, 29 / — | 40–115 MB | Bun 102 MB |
| Go net/http | 24.6 / 13.8 | 2694, 109 / 3073, 39 | 18–38 MB* | ملف واحد 11.5 MB |
| Rust axum | 10.1 / 14.1 | 5129, 49 / 3674, 33 | 7–54 MB* | ملف واحد 4.1 MB |
\* عدا تقرير الملخص على SQLite (8 اتصالات قراءة × 64 MB ذاكرة صفحات، قابلة للضبط).

**التقرير الثقيل (ملخص يوم + ميزان مراجعة على 800 ألف سطر):** 125–145 ms للطلب الواحد على SQLite و300–340 ms على PostgreSQL، **في كل اللغات**. تحت 100 اتصال لم تحقق أي تقنية p95 < 100 ms (الطوابير 3–14 ثانية). أي أن **العلاج في نموذج البيانات والتنفيذ المتوازي، لا في اللغة**.

ما استنتجته:
- كل التقنيات تكفي للعمليات الشائعة (p95 < 60 ms)، والفرق بين أطر Node نحو ±15% فقط.
- Rust/Go: ذاكرة أقل بكثير وملف واحد صغير. ثمنهما: **نواة محاسبة ثانية** (أو ترجمة Rust إلى WASM لتطبيقات الحاسوب والهاتف، أي إعادة كتابة كاملة لـ 4,300 سطر من المنطق المختبر + كل الواجهة)، وهو بالضبط ما يهدد شرط «أرقام مطابقة بالمليم».
- على جهاز واحد كانت SQLite أسرع من PostgreSQL أو مساوية في كل شيء. ميزة PostgreSQL تشغيلية: كتّاب متزامنون كثيرون، اتصال شبكي، نسخ مستمر (PITR)، عزل صفوف (RLS) للمنظمات، نسخ متماثلة.
- عملية Node الواحدة تتوقف كلها خلف استعلام بطيء؛ Go وحده ألغى الاستعلام حين انقطع العميل. إذاً في Node: **التقارير في عمّال منفصلين إلزامياً**.

## 4. مقارنة الواجهة (مقاس على هاتف متوسط محاكى)
نفس التطبيق RTL في 6 صيغ (Vite)، CPU ×4، شبكة 1.6 Mbps/150 ms، وسيط 5 تشغيلات. التفاصيل: `bench/arch-v2/frontend/REPORT.md`.

- **الجدول الكبير بطيء في كل الأطر** (3.2–3.8 ث)، وحصة الإطار 7–17% فقط؛ الباقي رسم المتصفح لـ 35 ألف خلية. **العرض الافتراضي** يجعل 10 آلاف صف تظهر في أقل من ثانية في كل الأطر.
- لا إطار أسرع للمستخدم من الكود الحالي، وكلها أثقل ذاكرة (4–6×). React الأثقل والأسوأ تمريراً.
- القرار: **نبقى بلا إطار** ونضيف TypeScript وخطوة بناء (esbuild) لتقسيم الكود (تحميل كل شاشة عند الحاجة) والعرض الافتراضي للجداول، ومسار طباعة منفصل يرسم كل الصفوف (موجود: `print-kit.js`).

## 6. البنية المقترحة
```
fuelpro/                          (مستودع واحد، npm workspaces)
├─ packages/core/                 TypeScript نقي: المال، القيود، المخزون، الوردية، التقارير، الصلاحيات، العزل
│    └─ ports.ts                  واجهة التخزين: query / exec / transaction(fn) — كلها async
├─ packages/db/                   Kysely + هجرات موحّدة + محوّلات:
│    ├─ pg.ts                     PostgreSQL (السيرفر)
│    ├─ sqlite-node.ts            node:sqlite (السيرفر الصغير + الاختبارات)
│    ├─ sqlite-tauri.ts           SQLite أصلي في Tauri (الحاسوب)
│    └─ sqlite-capacitor.ts       SQLite أصلي في Capacitor (الهاتف)
├─ packages/ui/                   الواجهة الحالية (vanilla) بـ TypeScript + esbuild + الطباعة
├─ apps/server/                   Node: HTTP + المصادقة + التقارير في عمّال + Docker/Caddy
├─ apps/desktop/                  غلاف Tauri: يشغّل core + ui محلياً، بلا سيرفر
├─ apps/mobile/                   غلاف Capacitor: core + ui محلياً
└─ tools/                         ترحيل البيانات، مقارنة التكافؤ، القياس، فحص الطباعة
```
- **في السيرفر:** المتصفح ← HTTP ← `core` ← محوّل PG. الصلاحيات والعزل في `core` (لا في الواجهة).
- **في الحاسوب والهاتف:** الواجهة تستدعي `core` مباشرة داخل التطبيق (نفس الدوال التي يستدعيها السيرفر) ← محوّل SQLite الأصلي. مستخدم محلي واحد أو أكثر على الجهاز، بكلمة مرور.
- **لماذا async:** محوّل PostgreSQL ومحوّل Capacitor غير متزامنين بطبيعتهما. النواة الحالية متزامنة (361 استدعاء). تحويلها إلى async يتم وحدة وحدة مع تمرير «المعاملة» صراحة لكل دالة.
- **اختبار التكافؤ:** سيناريو موحّد (بيع، وردية، سند، إلغاء، إقفال سنة...) يُشغّل على كل المحوّلات، وتُقارن كل الإجابات والتقارير بايتاً ببايت (امتداد `scripts/compare-dump.js`). أي فرق = فشل CI.

## 7. البنية التحتية والأمان والتحديث
- **السيرفر بأمر واحد:** `curl … | sudo bash` يثبّت Docker Compose (app + PostgreSQL + Caddy بشهادة HTTPS تلقائية). يبني على `deploy/vps` الحالي.
- **النسخ الاحتياطي:** `pg_dump` يومي + WAL مستمر للاستعادة لأي لحظة، ونسخة خارج السيرفر (Google Drive الحالي). هدف الاستعادة الكاملة < 10 دقائق، يُقاس في المرحلة 1.
- **المراقبة:** `/healthz` + مقاييس (زمن الطلبات، أخطاء، حجم القاعدة) + تنبيه عند التوقف.
- **التحديث بلا توقف:** نسختان من التطبيق خلف Caddy، هجرات «توسيع ثم تقليص» (expand/contract)، ونسخة احتياطية قبل كل تحديث مع رجوع تلقائي (كما يفعل `fuelpro-update` اليوم).
- **العزل:** كل استعلام مقيّد بالمنظمة في `core`، و**RLS في PostgreSQL** كطبقة ثانية.
- **المصادقة:** passkeys (WebAuthn) + TOTP الموجود. **المحلي:** تشفير اختياري للقاعدة بكلمة مرور (SQLCipher). سجل التدقيق كما هو.
- **تحديث المحلي:** الحاسوب: محدّث Tauri موقّع؛ الهاتف: المتجر أو ملف APK. قبل كل تحديث نسخة احتياطية للقاعدة، والهجرة في معاملة.

## 9. ما يحتاج قرارك
1. **التقارير الثقيلة:** القاعدة ADR-23 تمنع تخزين أي أرصدة أو مجاميع. اقتراحي **احترامها**: التقارير في عمّال منفصلين + فهارس، بهدف p95 أقل من ثانية للتقرير الثقيل (لا 100 ms). البديل الأسرع جداً (مجاميع يومية محسوبة في نفس معاملة القيد، مع فحص تطابق يومي) يتطلب إذنك صراحة لأنه يمس ADR-23.
2. **المتاجر والتوقيع:** نشر تطبيق الهاتف على Google Play يحتاج حساب مطوّر (رسم لمرة واحدة)، وApp Store حساباً سنوياً. وتوقيع مثبّت Windows/macOS يحتاج شهادة. هل نبدأ بـ Android (ملف APK مباشر) والحاسوب Windows أولاً؟
3. **السيرفر الحالي:** هل يبقى على SQLite حتى المرحلة 7 (اقتراحي)، ثم PostgreSQL؟
