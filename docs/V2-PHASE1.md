# FuelPro v2 — المرحلة 1: البيع والوردية بالأنماط الثلاثة

التاريخ: 2026-11-27 · الفرع: `claude/v2-phase1` · التصميم: `docs/ARCHITECTURE-V2.md` (ADR-30..39)

النظام الحالي (v1 في `src/` و`public/`) **لم يتغيّر** ويبقى هو المستخدَم في المحطة. كل عمل v2 داخل مجلد `v2/` المستقل،
ويُختبر في CI بملف مستقل `.github/workflows/v2.yml`.

## 1. ما أُنجز

| الجزء | المكان | الحالة |
|---|---|---|
| النواة: المال، الصلاحيات، القيود المزدوجة، المخزون بالمتوسط المرجّح، الإعداد، البيع، الإلغاء، الوردية (فتح/إغلاق/اعتماد/إلغاء الاعتماد/إعادة الفتح)، ميزان المراجعة | `v2/packages/core` | VERIFIED |
| طبقة البيانات: هجرات Kysely واحدة للمحرّكين + حُرّاس القيود داخل القاعدة (SQLite وPostgreSQL) | `v2/packages/db` | VERIFIED |
| مشغّل SQLite غير متزامن للنسخ المحلية (قفل واحد، `BEGIN IMMEDIATE`) | `v2/packages/db/src/sqlite-async.ts` | VERIFIED (بمحاكاة الجسر) |
| الواجهة المشتركة (عربية، بنفس ألوان v1 وخطه) | `v2/packages/ui` | VERIFIED في Chromium |
| نسخة الخادم: PostgreSQL أو SQLite | `v2/apps/server` | VERIFIED |
| نسخة سطح المكتب: Tauri 2 + Rust (rusqlite) + ملف SQLite محلي، بلا إنترنت | `v2/apps/desktop` | VERIFIED على Linux؛ Windows يُبنى في CI |
| نسخة الهاتف: Capacitor + SQLite أصلي، بلا إنترنت | `v2/apps/mobile` | يُبنى APK في CI؛ **لم يُجرَّب على هاتف حقيقي** (KI-23) |
| أداة النقل من v1 مع البرهان | `v2/tools/migrate-v1.ts` | VERIFIED على بيانات demo |

## 2. البرهان على تطابق الأرقام

`v2/tests/parity.test.ts`: سيناريو واحد (124 عملية ناجحة + 30 عملية مرفوضة: وردية مطلوبة، سقف الائتمان، عداد غير متزايد،
مخزون غير كافٍ، خصم أكبر من المبلغ، مستند ملغى، وردية مغلقة، معرّف من منظمة أخرى، تكرار نفس البيع…) بثلاث نسب ضريبة،
يُشغَّل على v1 وعلى v2 ثم تُقارن **كل** الصفوف: المبيعات، حركات المخزون، الخزانات، المضخات، الورديات وعداداتها، القيود وسطورها،
ميزان المراجعة، أرصدة العملاء، الحسابات، سجل التدقيق، ونتيجة كل عملية ورمز كل خطأ.

| المحرّك | النتيجة |
|---|---|
| v2 على SQLite (الخادم/الاختبار) | مطابق لـ v1 حتى أصغر وحدة — بذرتان |
| v2 على SQLite عبر جسر سطح المكتب/الهاتف | مطابق |
| v2 على PostgreSQL 16 | مطابق |

وفي `v2/tests/invariants.test.ts` على المحرّكات الثلاثة: القيد المرحّل لا يُعدَّل ولا يُحذف (القاعدة نفسها ترفض)،
القيد غير المتوازن مرفوض، العملية الفاشلة لا تترك أثراً، معرّف منظمة أخرى = «غير موجود»، الكاشير لا يعطي خصماً،
و40 بيعاً في اللحظة نفسها على مضخة واحدة بلا ضياع في العداد أو المخزون أو القيود، ونفس البيع من جهازين = بيع واحد.
**المجموع: 21 اختباراً ناجحاً.** واختبارات v1 كما هي: 94 ناجحاً + 1 متخطّى.

## 3. أداة النقل (`tools/migrate-v1.ts`)

تنسخ من ملف v1 (نسخة احتياطية، للقراءة فقط) إلى v2 مع الإبقاء على كل المعرّفات، ثم تحسب على الجهتين: عدد المبيعات
والقيود والسطور والحركات والورديات، مجموع المدين والدائن، ميزان المراجعة لكل محطة ولكل حساب، أرصدة الصناديق، أرصدة العملاء،
أرصدة الخزانات وحركاتها، ومبيعات كل يوم. **النسخ والبرهان في معاملة واحدة: أي فرق ⇒ تراجع كامل، والهدف يبقى فارغاً، ورمز خروج 2.**
لا تنسخ كلمات المرور ولا الجلسات ولا أسرار التحقق الثنائي، وترفض القراءة من `data/fuelpro.db` مباشرة.

## 4. الأداء قبل/بعد (نفس سنة demo، جهاز واحد بـ 4 أنوية يشغّل الخادم وقاعدة البيانات ومولّد الحِمل معاً)

### 100 مستخدم يعملون فعلاً (طلبات عشوائية، نحو طلبين في الثانية لكل مستخدم، 9 قراءات لكل بيع)
| | p50 | p95 | p99 |
|---|---|---|---|
| v1 (الحالي) | 9.9 ms | 98 ms | — |
| v2 SQLite | 2.0 ms | **5.3 ms** | — |
| v2 PostgreSQL | 2.7 ms | **7.5 ms** | — |

### أقصى ضغط (100 اتصال بلا توقف — اختبار تحمّل، ليس استخداماً واقعياً)
| العملية | v1 طلب/ث · p95 | v2 SQLite | v2 PostgreSQL |
|---|---|---|---|
| قائمة آخر 50 بيعاً | 1492 · 83 ms | 1277 · 98 ms | 972 · 122 ms |
| الوردية الحالية ومجاميعها | 1352 · 91 ms | 3048 · 49 ms | 1988 · 68 ms |
| خليط يوم عمل (9 قراءات + بيع على كل المضخات) | 351 · 247 ms | 794 · 163 ms | 1302 · 141 ms |
| بيع، و100 اتصال على **مضخة واحدة** (أسوأ حالة) | 605 · 231 ms | 486 · 194 ms | 207 · 551 ms |
| ذاكرة الخادم القصوى | 377 MB | 205 MB | 219 MB |

قراءة الأرقام: تحت الضغط الأقصى يصير الزمن ≈ عدد الاتصالات ÷ الإنتاجية (100 اتصال ÷ 1000 طلب/ث = 100 ms) أياً كان النظام،
لذلك معيار «p95 < 100 ms لـ 100 مستخدم» يُقاس بالاختبار الواقعي الأول، وv2 يحققه بفارق كبير. السطر الأخير متعمَّد كأسوأ حالة:
على PostgreSQL يُقفل صف المضخة والخزان أثناء البيع (حتى لا يضيع عداد أو لتر)، فمئة بيع متزامن على مضخة واحدة تنتظر بعضها؛
في المحطة لا يحدث ذلك (البيع على المضخة الواحدة كل دقيقة تقريباً)، وخليط يوم العمل على كل المضخات أسرع من v1.

## 5. كيف تجرّب

- **CI** يبني في كل PR: مثبّت Windows (`.exe` و`.msi`)، حزمة Linux (`.deb`)، و**APK للأندرويد** — من صفحة الـ PR ← Checks ← v2 ← Artifacts.
  هذه نسخ تجريبية غير موقّعة: Windows سيحذّر «ناشر غير معروف»، والأندرويد يطلب السماح بالتثبيت من مصدر غير معروف.
- أول فتح يعرض «إعداد المحطة» (اسم، وقود، سعر، خزان، مضخات) ثم شاشة البيع والوردية. البيانات تبقى على الجهاز فقط.
- الخادم محلياً: `cd v2 && npm ci && node tools/build.ts server && V2_DB=./v2-data/demo.db npm start` ثم افتح الرابط المطبوع.

## 6. ما لم يُنجز في هذه المرحلة (مخطط له)

- الدخول الحقيقي (مفاتيح المرور + TOTP، ADR-37): خادم v2 الآن محمي برمز واحد ويستمع على 127.0.0.1 فقط؛ النسخ المحلية مستخدم واحد. **لا يُستعمل v2 لبيانات حقيقية بعد.**
- باقي الوحدات (المخزون والتوريد، العملاء والتحصيل، الصناديق والسندات، التقارير، الطباعة، الرواتب) — المرحلة 2 فما بعد، وحدة وحدة بنفس طريقة البرهان.
- النسخ الاحتياطي اليدوي بين الأنماط (تصدير/استيراد ملف) — مع وحدة الإعدادات.
- التقارير الثقيلة في worker threads (ADR-33) — تبدأ مع وحدة التقارير.
- تجربة APK على هاتف حقيقي وتوقيع المثبّتات.

## 7. ما يحتاج قرارك

1. **جرّب APK على هاتفك وملف Windows على اللابتوب** من الـ Artifacts، وأخبرني بما ظهر (يفتح؟ الإعداد؟ البيع؟ الإغلاق؟). هذا ما لا أستطيع التحقق منه من هنا.
2. **المرحلة 2: أي وحدة أولاً؟** اقتراحي: المخزون والتوريد (التوريدات، الجرد، التحويل) لأنها تكمل دورة الوقود مع البيع، ثم العملاء والتحصيل.
3. **التوقيع:** متى تريد مثبّتاً موقّعاً؟ Windows يحتاج شهادة توقيع (مدفوعة سنوياً)، وGoogle Play يحتاج حساب مطوّر (25$ مرة واحدة). حتى ذلك الحين تبقى النسخ تجريبية.
